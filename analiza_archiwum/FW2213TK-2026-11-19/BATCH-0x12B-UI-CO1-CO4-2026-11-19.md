# BATCH: 0x12B drives the actual TOUCH Heating UI menu — 2026-11-19

## Major new result

Tracing the active object type field forward from +0x12B found a direct UI consumer: `FUN_0803E714`.

It obtains the singleton object with `FUN_080314BA()` and switches directly on `object+299` (`+0x12B`).

### 1. Classes 1..4 share one concrete Heating UI branch

The switch has an explicit combined branch:

- case 1
- case 2
- case 3
- case 4

All four execute the same UI construction path:

`FUN_0803EFDA(param_1, DAT_0803EEC0 + 0x62, 0x0C)`

and then later each selected parameter ID is read through:

`FUN_08036FF2(parameter_context, parameter_id)`

and sent into `FUN_0804842C(...)` for the rendered UI entries.

This is strong firmware-level evidence that +0x12B values 1..4 are not merely abstract object classes: they select the Heating/CH UI mode whose parameter data is instance-aware.

### 2. Instance is still supplied by +0x12C, while type selects the UI family

`FUN_0803E714` switches on +0x12B, but its parameter reads use `FUN_08036FF2`.

Earlier hard tracing established that `FUN_08036FF2` uses the object's +0x12C as the instance offset for the first parameter table.

Therefore the two fields have now been separated by actual consumers:

- `+0x12B` = selects the object/UI class (including Heating CO1..CO4 class branch)
- `+0x12C` = selects the concrete instance inside the parameter families

This is materially stronger than the earlier field-name inference.

### 3. The same UI branch does not need four duplicated functions

The firmware deliberately implements cases 1..4 together in `FUN_0803E714`. The differentiation comes from instance-aware parameter lookup, not four copies of the whole UI builder.

So the runtime model is:

    class 1..4
        -> same Heating UI builder
        -> +0x12C selects instance
        -> FUN_08036FF2(base_parameter, instance)
        -> concrete CO1/CO2/CO3/CO4 parameter record
        -> FUN_0804842C -> rendered value/widget

This explains why the same screen geometry can be reused while the underlying parameter record changes. Geometry itself remains an identification aid, not the primary mechanism.

### 4. Static CO1..CO4 registration now connects cleanly to this UI consumer

Existing hard registration evidence:

- `0x2032..0x2035`
- `0x2048..0x204B`
- `0x2064..0x2067`

are statically registered as four-instance parameter families.

Existing parameter lookup evidence:

- `0x2032 + instance - 1`
- `0x2048 + instance - 1`
- `0x2064 + instance - 1`

Now `FUN_0803E714` is a direct consumer of the class 1..4 object path and calls the same instance-aware parameter engine.

Thus we have a real continuous chain:

    classification
      -> +0x12B = 1..4
      -> +0x12C = 1..4
      -> FUN_0803E714 class 1..4
      -> FUN_08036FF2(..., parameter_id)
      -> base + instance - 1
      -> CO1..CO4 static record
      -> UI value

### 5. This narrows the missing activation boundary

The remaining unknown is no longer whether +0x12B/+0x12C represent usable CO instances. They demonstrably do.

The key unresolved boundary is specifically:

    configuration / object-list selection
          -> param_2
          -> DAT_0803C218[param_2]
          -> value 1..4
          -> +0x12B/+0x12C

We still must not assert `0x2105 -> C064` without code evidence.

### 6. Important architectural consequence

The firmware is using a generic polymorphic module object with a shared Heating UI implementation. Four CO circuits are represented through the instance dimension of a common parameter engine, while +0x12B chooses the relevant object class.

This is now much closer to a 1:1 behavioral model than a simple CAN-ID map.
